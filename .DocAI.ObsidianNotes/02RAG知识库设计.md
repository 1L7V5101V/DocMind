## 2.1 文档向量化设计

### 解决了什么问题

文档向量化在项目中主要解决的是“用户上传或导入的文档如何变成可被语义检索的知识”的问题。

**核心矛盾：** 原始文档只是普通文本，直接交给大模型有两个问题：
- 受上下文长度限制，无法处理长文档
- 用户提问时难以精准定位答案位置

**解决方案：** KnowledgeBase 统一文档入库流程
1. 保存原文和元数据
2. DocumentSegmenter 对文档切分
3. DocumentVectorizer 调用 DashScope Embedding 生成向量
4. 写入 VectorStore

**效果：** 长文档拆成多个独立语义的知识片段，检索以片段为单位而非整篇文档，提升召回准确性

### 为什么这么设计

| 设计选择                            | 为什么这么定                                           |
| ------------------------------- | ------------------------------------------------ |
| **文档分段 + Embedding 向量化 + 向量索引** | 文档 AI 场景知识来源多样（技术文档、报告、会议纪要、教程等），分段能兼顾文档结构和语义完整性 |
| **不直接向量化整篇文档**                  | 整篇向量化后用户问具体问题会召回整篇相关但局部无关的内容                     |
| **不只做关键词索引**                    | 关键词索引无法处理用户问题和文档表达不一致的情况（如同义改写）                  |
| **采用多策略分段（章节/固定长度/语义/自动）**      | 章节分段保留文档结构，固定长度控制片段大小，语义分段保持语义完整，自动策略根据文档特征择优    |

### 具体怎么设计的

**分段配置（SegmentConfig）：**
- 固定长度分段：chunkSize=500，overlap=50
- 章节分段：最小长度 100，最大长度 5000
- 语义分段：目标长度 300，最小长度 100，相似度阈值 75

**分段策略（DocumentSegmenter）：**
- 支持 AUTO、FIXED_LENGTH、CHAPTER、SEMANTIC、[[HYBRID分段策略]] 五种策略
- [[AUTO分段策略]] 根据是否有章节标记、文档长度是否超过 2000 自动选择合适方式

**向量化（DocumentVectorizer）：**
- 调用 DashScope Embedding API，配置当前使用 text-embedding-v1，代码默认 text-embedding-v4

**存储：**
- 生成的向量、原文片段、元数据分别以 vector:、segment:、metadata:、doc:、content:、doc_segments: 等 key 存入 Redis
- 内存中构建 HNSW 索引，实现持久化存储 + 快速相似度检索

### 为什么不采用别的方式

| 方案                               | 不采用的原因                                                        |
| -------------------------------- | ------------------------------------------------------------- |
| **整篇文档直接向量化**                    | 召回结果过于粗糙，容易把无关上下文带入大模型                                        |
| **纯固定长度切分（唯一方案）**                | 文档带有章节/标题/Markdown 结构，机械切分破坏天然语义边界                            |
| **Milvus、Qdrant 等专业向量数据库（当前阶段）** | 已深度使用 Redis，Redis 持久化 + 内存 HNSW 已能支撑中小规模知识库，部署成本更低（[[向量数据库]]） |
| **上述设计（当前选择）**                   | 等知识规模、并发量、多实例一致性要求提高后再迁移到专业向量数据库                              |

## 2.2 检索策略设计

### 解决了什么问题

检索策略解决的是“用户提出问题后，系统如何从知识库中找到最相关知识片段”的问题。

**核心矛盾：** 直接让大模型自由发挥会依赖模型自身参数知识，可能产生幻觉，回答与项目文档不一致。

**解决方案：**
1. DocumentVectorizer 将用户问题转为查询向量
2. VectorStore 从已索引的知识片段中进行相似度搜索
3. 系统基于项目知识库内容回答，而非模型参数知识

**效果：** 减少幻觉，提高回答与项目文档的一致性

### 为什么这么设计
**[[多阶段检索策略]]**

| 设计选择                                        | 为什么这么定                                                                       |
| ------------------------------------------- | ---------------------------------------------------------------------------- |
| **向量召回 + [[BM25补充]] + [[Rerank 精排]]的多阶段策略** | 向量检索适合语义相近但表达不同的问题，[[BM25]] 适合接口名/类名/配置项等精确匹配，Rerank 用于候选结果中二次判断，兼顾语义召回和精确匹配 |
| **不只使用一种检索方式**                              | 知识库中既有自然语言文档，也有技术术语/代码说明/配置内容，单一检索方式很难兼顾                                     |
| **不把所有召回内容直接塞给大模型**                         | 上下文窗口有限，过多无关片段增加 token 成本并干扰模型判断                                             |
| **先扩大候选再 Rerank 压缩**                        | 先保证召回率，再提高精确率，更适合同答场景                                                        |

### 具体怎么设计的

KnowledgeBase 提供三种检索接口：

**基础检索（search）**
- query 向量化后交给 VectorStore，内部使用 HNSW 近似最近邻索引
- 采用 FLOAT_COSINE_DISTANCE 做余弦距离计算
- 先取比最终 topK 更多的候选，再按 userId、knowledgeBaseId 等 metadata 过滤（用户只能查自己知识库）

**混合检索（hybridSearch）**
- 同时执行向量检索 + 简化 BM25 检索
- 合并去重后返回候选结果

**重排序检索（hybridSearchWithRerank）**
- 由 Reranker 完成，支持 BM25_FUSION、CROSS_ENCODER、HYBRID 三种策略
- 配置启用 DashScope rerank，模型为 qwen3-rerank
- [[外部重排服务不可用时，降级到本地启发式重排]]，保证链路可用

### 为什么不采用别的方式

| 方案                         | 不采用的原因                                      |
| -------------------------- | ------------------------------------------- |
| **只采用向量检索**                | 语义接近可能把看似相关但不能回答的片段排在前面，接口名/配置项/文件名等精确内容不稳定 |
| **只采用关键词检索**               | 用户问题与文档存在同义表达时，漏掉语义相关但字面不一致的内容              |
| **所有召回内容直接塞给大模型**          | 上下文窗口有限，过多无关片段增加 token 成本并干扰模型判断            |
| **先扩大候选再 Rerank 压缩（当前选择）** | 先保证召回率再提高精确率，更适合同答场景                        |

## 2.3 知识更新机制

### 解决了什么问题

知识更新机制解决的是“文档变化后，知识库中的向量、分段和元数据如何保持同步”的问题。

**核心矛盾：** 只在首次上传时建立索引，后续文档修改/删除/重复上传不处理旧索引 → 用户检索到过期内容。

**解决方案：**
- KnowledgeIndexAgent 管理索引任务，将索引过程包装成可追踪的管道
- 通过内容 hash 判断文档是否真的变化
- 变化时才重新索引，避免重复索引和旧知识污染

**效果：** 保持知识内容新鲜度，避免重复计算

### 为什么这么设计

| 设计选择                               | 为什么这么定                                                     | **解释**                                       |
| ---------------------------------- | ---------------------------------------------------------- | -------------------------------------------- |
| **异步索引**                           | 向量化调用外部 Embedding 模型耗时且成本高，同步阻塞等待影响用户体验                    |                                              |
| **hash 去重（SHA-256 → contentHash）** | 避免文档未变化时重复向量化，减少不必要的模型调用成本                                 |                                              |
| **先删后建**                           | 内容变化时清理旧分段和向量再重新建立，保证检索内容与最新文档一致                           |                                              |
| **不采用全量重建**                        | 外部 Embedding 服务全量重建带来明显的时间成本、接口成本和服务压力                     | **增量重建**——每次只重建变化的那篇文档。                      |
| **不以 documentId 维护多版本**            | 在线问答场景通常优先需要最新知识；未来可扩展 version/status/effectiveTime 进行版本过滤 | 同一个 `documentId` 在知识库里**只有一份最新有效索引**，没有历史版本。 |

### 具体怎么设计的

**异步线程池（KnowledgeIndexAgent）**
- 维护异步线程池处理索引任务
- 任务经历 PARSING → EMBEDDING → INDEXED → FAILED 等状态
- 通过 Redis 保存任务快照，默认保留 7 天

**索引流程**
1. 计算 contentHash（SHA-256）
2. 补充 userId、knowledgeBaseId、tags、category 等元数据
3. 调用 KnowledgeBase 写入知识库

**增量更新**
- 发现同一 documentId 已存在且 hash 不同 → 先调用 removeDocument 删除旧 segment/向量/元数据/原文
- 再调用 addDocument 重新分段、向量化、写入

**删除索引（deleteIndex）**
- 同时调用 vectorStore.delete + knowledgeBase.removeDocument
- 确保 Redis 中的文档内容、分段内容、向量索引、映射关系全部清理

### 为什么不采用别的方式

| 方案                              | 不采用的原因                                                  |
| ------------------------------- | ------------------------------------------------------- |
| **每次全量重建整个知识库**                 | 依赖外部 Embedding 服务，全量重建带来明显的时间成本、接口成本和服务压力               |
| **只更新原文、不更新向量**                 | 向量仍表示旧内容，检索继续召回过期知识                                     |
| **无版本判断直接覆盖**                   | 没有 contentHash 无法判断文档是否真正变化，无法避免重复索引                    |
| **以 documentId 维护最新有效索引（当前选择）** | 在线问答场景优先需最新知识；未来可扩展 version/status/effectiveTime 实现版本过滤 |
