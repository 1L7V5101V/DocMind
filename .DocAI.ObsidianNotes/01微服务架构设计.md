## 一、微服务划分设计

### 解决了什么问题

**核心矛盾：** 单体应用代码庞大、部署耦合、开发冲突频繁、扩展成本高、单点故障导致全局崩溃

**解决方案：** 按业务领域拆分为独立微服务，每个服务独立部署、独立扩展、独立迭代

**效果：** 团队解耦独立开发、按需扩展节省资源、故障隔离不扩散

### 为什么这么设计

| 设计选择 | 为什么这么定 |
|---------|------------|
| **用户服务（user-service）** | 专注"谁"的问题——认证、权限、用户管理，与业务文档解耦 |
| **文件服务（file-service）** | 专注"存"的问题——上传下载、元数据、存储策略，不依赖业务逻辑 |
| **AI服务（ai-service）** | 专注"智"的问题——摘要、纠错、RAG，独立扩展应对CPU密集计算 |
| **文档服务（document-service）** | 专注"文"的问题——CRUD、版本、搜索，核心业务独立迭代 |
| **网关服务（gateway-service）** | 统一入口，集中处理路由、鉴权、限流，后端服务不对外暴露 |
| **标准接口通信（HTTP/消息队列）** | 内部实现可随时更换，不影响其他服务；不直接访问对方数据库 |

### 具体是怎么设计的

**项目结构：** 五个独立服务模块，各自独立代码仓库、Dockerfile、配置文件

**通信方式：** HTTP接口或消息队列，不存在直接调用对方数据库的情况

**统一入口：** 网关服务作为唯一入口，所有外部请求必须经过网关

### 为什么不采用别的方式

| 方案 | 不采用的原因 |
|------|------------|
| **单体架构** | 所有问题（代码膨胀、部署耦合、冲突频繁、扩展困难、故障全局扩散）都无法解决 |
| **ESB中心化架构** | 总线成为性能瓶颈和单点故障源 |
| **纳米服务（过度拆分）** | 维护成本极高，调用链复杂，排查问题困难，开发运维崩溃 |
| **按业务领域划分微服务（选择了这个）** | 明确职责边界，独立部署扩展，故障隔离

## 二、服务间通信设计

### 1. OpenFeign[[声明式]]调用，[[同步 RPC 调用]]

### 解决了什么问题

**核心矛盾：** 需手动拼接 HTTP URL、手动服务发现、手动负载均衡、手动处理超时和重试，样板代码散落各处污染业务逻辑

**解决方案：** OpenFeign 声明式接口——用 Java 接口描述调用目标，框架自动处理底层网络通信

**效果：** 面向接口而非 URL，业务代码整洁，替换实现只需改配置不改代码

### 为什么这么设计

| 设计选择 | 为什么这么定 |
|---------|------------|
| **声明式接口风格** | 面向接口而非 URL，符合面向对象设计原则 |
| **框架自动处理网络通信** | 开发者只需描述"调用哪个服务的哪个接口"，零样板代码 |
| **配置驱动实现切换** | 测试环境切生产环境只需改配置，不改代码 |

### 具体是怎么设计的

**FeignGlobalConfig：**
- **连接超时：** 10秒
- **读取超时：** 60秒（AI服务处理文档需较长时间）
- **重试策略：** 失败后100ms开始重试，最多3次
- **间隔考量：** 太短给下游压力，太长影响用户体验

### 为什么不采用其他方式

| 方案 | 不采用的原因 |
|------|------------|
| **Dubbo** | 强调高性能和同步阻塞调用，学习曲线较陡，Spring 生态集成度不如 OpenFeign |
| **gRPC** | 需要定义 proto 文件，性能好但增加了额外复杂度，对文档服务场景过于重量级 |
| **RestTemplate 手动处理** | 代码冗长，每个团队实现可能不一致，难以统一 |
| **OpenFeign（选择了这个）** | 声明式风格，与 Spring Cloud 生态无缝集成，零额外运维成本 |

## 2. RabbitMQ异步消息队列

### 解决了什么问题

**核心矛盾：** 文件上传高频操作，同步等待AI分析需几十秒体验差；文件服务依赖AI可用性，AI故障阻塞上传；突发流量冲垮AI服务

**解决方案：** 文件服务发送事件到队列立即返回"上传成功"，AI服务按自身节奏消费处理

**效果：** 时间解耦（不同步等待）、空间解耦（不感知对方位置）、流量削峰（队列缓存）

### 为什么这么设计

| 设计选择 | 为什么这么定 |
|---------|------------|
| **生产者-消费者模式** | 文件服务生产事件立即返回，AI服务按自身节奏消费 |
| **消息队列解耦** | 时间解耦（不同步等待）、空间解耦（不感知对方）、流量削峰（缓冲突发） |

### 具体是怎么设计的

**交换机：** ai.exchange

**队列：** ai.task.queue（常规AI任务）、ai.alert.queue（告警消息）

**流程：** 文件上传成功 → 发送消息路由键 "task" → AI服务监听队列消费

**优势：** 灵活扩展消费者提高吞吐量，可新增队列处理不同类型任务

### 为什么不采用其他方式

| 方案 | 不采用的原因 |
|------|------------|
| **Kafka** | 偏向大数据场景，持久化机制复杂，延迟高于RabbitMQ，不适合文档处理实时性要求 |
| **线程池异步处理** | 服务重启时未处理任务丢失，无法持久化 |
| **定时任务轮询** | 实时性差，无任务时也要查询数据库浪费资源 |
| **RabbitMQ（选择了这个）** | 轻量级、配置简单、延迟低、持久化可靠，满足文档处理实时性要求 |

## 3. [[Nacos服务]]发现与配置管理

### 解决了什么问题

**核心矛盾：** 微服务实例地址动态变化（扩缩容、故障重启、容器漂移），硬编码地址变更成本高易出错；改配置需重启服务，生产环境无法随意重启

**解决方案：** Nacos 同时充当服务发现注册中心和配置中心，服务启动时注册自身地址，调用方通过服务名解析；配置集中管理，修改后自动生效无需重启

**效果：** 服务地址解耦、配置动态刷新、零重启变更

### 为什么这么设计

| 设计选择 | 为什么这么定 |
|---------|------------|
| **服务发现（地址注册 + 心跳续约）** | 调用方只需服务名，Nacos自动解析可用地址，不可用服务自动移除 |
| **配置中心（集中管理 + 动态刷新）** | 修改配置在控制台操作，服务自动感知无需重启 |
| **健康检查（心跳机制）** | 未收到心跳的服务自动从可用列表剔除，保护调用方 |

### 具体是怎么设计的

**配置：** Nacos 服务器地址 nacos:8848，服务名 ai-service

**注册：** 服务启动自动注册到 Nacos，定时发送心跳续约

**失效剔除：** 未收到心跳的服务自动从可用列表移除，调用方不会拿到故障地址

### 为什么不采用其他方式

| 方案 | 不采用的原因 |
|------|------------|
| **Consul** | 多语言友好但 Spring Cloud 集成不如 Nacos 顺畅，需额外配置 |
| **Eureka** | 已停止维护，不再是 Spring Cloud 官方推荐 |
| **Zookeeper** | 临时节点适合分布式锁，用于服务发现需自实现大量逻辑，性能不如 Nacos |
| **静态配置文件** | 完全无法应对服务实例动态变化 |
| **Nacos（选择了这个）** | 同时解决服务发现和配置管理，Spring Boot 集成友好，社区活跃文档丰富 |

## 三、[[API网关设计]]

### 解决了什么问题

**核心矛盾：** 前端需记住每个后端服务地址，暴露内部架构不安全；每个服务重复实现鉴权、跨域、限流，代码重复难维护

**解决方案：** 网关作为统一入口，前端只与网关通信；网关集中处理鉴权、路由、限流，下游服务只关注业务

**效果：** 内部架构不对外暴露、跨领域逻辑统一管理、下游服务专注业务

### 为什么这么设计

| 设计选择 | 为什么这么定 |
|---------|------------|
| **统一入口（所有请求先到网关）** | 集中验证 JWT 合法性，按路由规则转发；类比办公楼门禁系统 |
| **故障/过载保护** | 服务负载过高或故障时主动拒绝请求，保护下游服务 |
| **Spring Cloud Gateway** | 原生集成 Spring Cloud（Nacos 服务发现、负载均衡），WebFlux 非阻塞高性能 |

### 具体是怎么设计的

**AuthGlobalFilter（核心过滤器）：**
- **白名单：** 登录和注册接口不验证直接放行
- **JWT 验证：** 其余请求必须携带有效 token
- **信息传递：** 验证后将用户ID、用户名、角色放入请求头传递下游，下游无需再解析 token
- **优先级：** -100，确保在路由之前执行

### 为什么不采用其他方式

| 方案 | 不采用的原因 |
|------|------------|
| **每个服务单独做鉴权** | 代码重复，各服务实现可能不一致，存在安全漏洞 |
| **NGINX 反向代理** | 难以集成 Spring Cloud 生态，服务发现、动态路由能力弱 |
| **Kong API 网关** | 需要单独部署维护，学习成本高，对现有架构改动大 |
| **Spring Cloud Gateway（选择了这个）** | 原生集成 Spring Cloud（Nacos 服务发现、负载均衡），过滤器链灵活，WebFlux 非阻塞高性能，零额外运维成本 |


## 四、整体设计思路

整个架构的设计原则是让每个服务专注于自己的业务，把跨领域的关注点（认证、流量控制、服务发现）抽离出来由专门的组件处理。

**同步调用场景用OpenFeign**是因为它的声明式风格让接口调用看起来就像调用本地方法一样自然，调试和测试都比较方便，而且跟Spring Cloud生态无缝集成。
**异步场景用RabbitMQ**是因为它足够轻量，配置简单，界面友好，运维成本低，能够满足业务对实时性的要求。
**服务治理用Nacos**是因为它同时解决了服务发现和配置管理两个问题，对Spring Boot应用友好，社区活跃文档丰富。

这套架构能让团队高效协作，不同服务可以由不同团队负责开发、测试和部署。可以根据各服务的负载情况独立扩展，比如AI服务CPU密集就多部署几个，文件服务IO密集就用更高性能的存储。系统整体具备容错能力，某个服务故障不会扩散到全局。
