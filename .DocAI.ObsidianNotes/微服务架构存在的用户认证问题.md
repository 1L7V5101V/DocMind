**核心矛盾：** 微服务架构下 Session 无状态认证困难，跨服务认证不统一，Token 过期需用户频繁重新登录，身份信息无法在服务间高效传递

**1. Session 无状态认证困难**
- 传统单体应用：Session 存储在一台服务器内存中，请求始终打到同一台机器
- 微服务下：服务实例多、动态扩缩容、负载均衡分发，无法保证同一用户的请求落在同一实例
- 解决方向：要么引入 Redis 集中存储 Session（增加依赖和复杂度），要么彻底抛弃 Session 用无状态 Token

**2. 跨服务认证不统一**
- 每个微服务独立开发、独立部署，如果没有统一规范，各服务可能各自实现一套认证逻辑（有的用 Session、有的用自定义 Token、有的用 API Key）
- 用户请求跨服务调用时，每个服务都要重新认证，且认证方式不同，集成和维护成本极高
- 所以需要网关层集中鉴权 + 统一的认证标准（如 JWT）

**3. Token 过期需用户频繁重新登录**
- 如果使用单 Token 且有效期设得短（比如 30 分钟），用户在长时间操作中 Token 过期后请求被拒，被迫重新登录
- 如果设得长（比如 7 天），则泄露风险大
- 微服务中一个用户操作可能涉及多个服务调用，Token 过期导致连锁失败
- 所以需要**双 Token 机制**：短有效期的 AccessToken + 长有效期的 RefreshToken，RefreshToken 负责无感刷新，用户不需要重新登录

**4. 身份信息无法在服务间高效传递**
- 认证只在网关或某个服务完成，但下游服务（如订单服务、用户服务）也需要知道当前请求是谁发起的
- 没有统一传递机制的话，每个下游服务都要各自去解析 Token、查数据库获取用户信息，增加重复开销和延迟
- 所以需要在网关层解析 Token 后，通过请求头（X-User-Id / X-Username / X-Role）将用户身份透传给下游服务，下游直接取用
