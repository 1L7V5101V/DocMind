## 一、路由规则设计

### 解决了什么问题

解决了服务路由映射问题，将外部请求根据路径转发到对应的微服务；解决了路径前缀匹配问题，支持灵活的路由规则配置；解决了服务发现与负载均衡问题，支持动态发现服务实例并分发请求。

### 为什么这么设计

采用Spring Cloud Gateway作为网关组件，内置强大的路由规则引擎；支持服务发现模式（lb://）和直连模式（http://）两种模式，便于开发和生产环境灵活切换；使用配置驱动的方式配置路由，无需代码硬编码；集成Nacos服务发现，自动感知服务实例变化；支持负载均衡策略默认使用轮询方式，简单高效。

### 具体怎么设计的

- 服务路由映射 ：通过Java配置类定义路由规则，将/api/users/**路径映射到用户服务，/api/files/**路径映射到文件服务，/api/ai/**路径映射到AI服务，/api/documents/**路径映射到文档服务。路由目标地址通过配置参数管理，支持动态调整。

```
// 路由配置示例
.route("user", r -> r.path("/api/users/
       **").uri(userServiceUri))
.route("file", r -> r.path("/api/files/
       **").uri(fileServiceUri))
```

- 路径前缀匹配 ：采用Ant风格路径匹配规则，支持**通配符，如/api/users/**匹配该前缀下的所有路径。网关将匹配的路径原样转发到下游服务，下游服务无需感知网关的存在。
- 负载均衡策略 ：支持两种路由模式，服务发现模式使用lb://前缀，自动从Nacos获取服务实例列表，使用默认轮询策略分发请求；直连模式使用 http://前缀，直接转发到指定地址，适合开发调试环境。路由目标地址可通过配置文件灵活切换。

### 为什么不采用别的方式

- 不采用Nginx作为网关，因为Nginx配置修改需要重启，不支持Java生态的服务发现和过滤器链；
- 不采用Zuul1.x，因为是阻塞IO模型，性能不如Spring Cloud Gateway的响应式模型；
- 不采用手动写代码转发，因为可维护性差，缺少成熟组件的丰富功能。

## 二、全局过滤器设计

### 解决了什么问题

解决了JWT认证问题，在网关层统一鉴权，避免各服务重复实现；解决了请求日志记录问题，统一记录所有请求信息；解决了请求头处理问题，将用户信息安全传递给下游服务。

### 为什么这么设计

采用全局过滤器实现横切关注点，符合网关层统一处理；白名单机制，登录注册等接口免认证；使用Ordered接口控制过滤器优先级，确保鉴权优先执行；通过请求头传递用户信息，下游服务直接使用；集成RabbitMQ发送网关日志和告警，异步解耦。

### 具体怎么设计的

- JWT认证过滤器 ：实现GlobalFilter和Ordered接口，优先级设为-100优先执行。拦截所有请求，检查白名单路径，白名单直接放行。从请求头获取Bearer Token，验证Token有效性，无效返回401。验证通过后将用户ID、用户名、角色添加到请求头（X-User-Id、X-Username、X-Role）传递给下游服务。
- 请求日志记录 ：所有请求都记录日志，包括路径、方法、用户ID、时间戳，通过RabbitMQ发送到消息队列。对未授权请求、无效令牌等异常情况发送告警消息。

```
// 白名单配置示例
private static final List<String> 
WHITE_LIST = List.of(
    "/api/users/login",
    "/api/users/register",
    "/api/users/refresh"
);
```

- 请求头处理 ：验证Token成功后，修改请求对象，将用户信息添加到新的请求头中，下游服务从请求头中直接读取用户信息，无需再次解析Token。同时支持CORS跨域配置，允许指定来源、方法、请求头，允许携带凭证。

### 为什么不采用别的方式

- 不在每个服务中做鉴权，因为重复代码，维护成本高，网关统一鉴权效率更高；
- 不采用Session，因为是无状态架构，Token方式更适合；
- 不直接在请求参数传递用户信息，因为不安全，请求头更规范。

## 三、限流熔断设计

### 解决了什么问题

解决了限流问题，防止流量突增导致服务过载；解决了分布式限流问题，多实例网关统一限流；解决了服务降级问题，服务异常时提供降级方案。

### 为什么这么设计

预留Sentinel集成能力，配置中已引入sentinel.enabled配置项，默认关闭；预留Redis分布式限流配置，包括开关、前缀、默认限流阈值；配置文件设计支持灵活配置限流规则；当前版本优先保证核心功能可用，后续可逐步完善限流熔断能力。

### 具体怎么设计的

- Sentinel限流规则 ：配置文件中预留Sentinel配置，支持启用/禁用，后续可配置QPS限流、线程数限流、热点限流等规则，可配置流控模式（直接、关联、链路），可配置流控效果（快速失败、预热、排队等待）。
- Redis分布式限流 ：配置文件中预留Redis限流配置，包括开关、Redis键前缀、默认限流速率、默认突发流量限制。使用Redis作为限流存储，实现多网关实例共享限流数据，支持基于令牌桶或漏桶算法。

```
# 限流配置示例
custom:
rate-limit:
enable: true
redis-key-prefix: gateway:rate-limit
default-rate: 100
default-burst: 200
```

- 服务降级策略 ：预留降级策略扩展点，服务超时或异常时，可返回默认值、缓存数据、友好提示等，避免级联故障。

### 为什么不采用别的方式

- 不采用Guava RateLimiter，因为是单机限流，不支持分布式；
- 不直接在每个服务中做限流，因为网关统一限流更高效，可保护整个系统；
- 不一开始就实现复杂的限流，因为当前阶段先保证核心功能可用，后续可根据需要逐步完善。

## 总结

网关设计采用Spring Cloud Gateway作为核心组件，通过配置驱动的路由规则，全局过滤器实现鉴权、日志、跨域，预留限流熔断扩展点。当前版本已实现路由转发、JWT鉴权、请求日志、CORS配置，限流熔断功能已预留配置和扩展能力，后续根据需要逐步完善。
