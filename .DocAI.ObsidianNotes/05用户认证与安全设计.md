## 一、JWT鉴权设计

### 解决了什么问题

**核心矛盾：** 微服务架构下 Session 无状态认证困难，跨服务认证不统一，Token 过期需用户频繁重新登录，身份信息无法在服务间高效传递（[[微服务架构存在的用户认证问题]]）

**解决方案：** 双 Token 机制（[[AccessToken]] 30min + [[RefreshToken]] 7天），网关层集中鉴权，JWT 操作封装为公共模块，通过请求头传递用户信息

**效果：** 无状态认证不依赖服务端存储、跨服务统一认证机制、无感刷新 Token、下游服务无需重复解析 Token 即可获取用户身份

### 为什么这么设计

| 设计选择                                                | 为什么这么定                                   |
| --------------------------------------------------- | ---------------------------------------- |
| **双 Token 机制（AccessToken 30min / RefreshToken 7天）** | 短有效期降低泄露风险，长有效期减少用户重新登录频率，平衡安全性与体验       |
| **网关层集中鉴权**                                         | 各服务无需重复实现鉴权逻辑，统一管理白名单路径和 Token 验证，减轻服务压力 |
| **请求头传递用户信息（X-User-Id / X-Username / X-Role）**      | 下游服务直接使用，避免各服务重复解析 Token                 |
| **JWT 操作封装为公共模块**                                   | 各服务复用同一套 Token 生成、解析、验证逻辑                |

### 具体是怎么设计的

**Token 生成与解析（JwtUtils）：**
- AccessToken 包含用户 ID、用户名、角色信息
- RefreshToken 仅包含用户 ID
- 验证时检查签名和过期时间，解析时提取用户信息

```java
String accessToken = JwtUtils.generateToken(user.getId(), user.getUsername(), user.getRole());
String refreshToken = JwtUtils.generateRefreshToken(user.getId());
```

**Token 刷新机制：**
- 提供专门刷新接口，用户使用 RefreshToken 换取新 AccessToken
- 刷新时验证 RefreshToken 有效性，查询用户信息后生成新 AccessToken 返回，无需重新登录

**Token 过期与验证：**
- Token 自带过期时间字段，验证时自动检查是否过期
- 网关层配置白名单路径（登录、注册、刷新令牌等），免认证放行

**网关鉴权：**
- AuthGlobalFilter 拦截所有请求，检查白名单路径
- 提取并验证 Bearer Token，验证通过后将用户 ID、用户名、角色添加到请求头（X-User-Id、X-Username、X-Role）传递下游
- 同时记录网关日志和告警信息

### 为什么不采用其它方案

| 方案                        | 不采用的原因                                                                           |
| ------------------------- | -------------------------------------------------------------------------------- |
| **Session 认证**            | 服务端需要存储状态，跨服务共享 Session 复杂，水平扩展困难，不适合微服务架构                                       |
| **OAuth2.0 完整流程**         | 过度设计，当前需求不需要，增加复杂度与学习成本                                                          |
| **Redis 存储 Token（当前阶段）**  | 增加 Redis 依赖，当前双 Token 设计足够；黑名单机制后续可扩展（但是面试回答的时候可以说引入了Redis，并介绍相关依赖，我后续也会更新这部分代码） |
| **双 Token + 网关鉴权（选择了这个）** | 无状态、集中鉴权、跨服务统一、扩展灵活                                                              |

## 二、安全配置设计

### 解决了什么问题

**核心矛盾：** API 服务面临 [[CSRF 攻击]]风险，前后端分离架构需要跨域支持，不同接口需要差异化权限控制，多个微服务需共享一致的安全配置

**解决方案：** 基础安全配置继承（BaseSecurityConfig） + 无状态会话 + 白名单机制 + 网关+服务双重安全

**效果：** 各服务继承统一安全配置避免重复代码，非敏感接口白名单放行，网关鉴权 + 服务层权限双重保护

### 为什么这么设计

| 设计选择                                               | 为什么这么定                   |
| -------------------------------------------------- | ------------------------ |
| **采用基础配置继承方式，BaseSecurityConfig提供通用的安全设置，各服务继承使用** | 避免重复代码                   |
| **无状态会话管理**                                        | 适合API服务，不依赖Session       |
| **配置白名单机制**                                        | 登录、注册、Swagger 文档等接口免认证访问 |
| **采用[[网关+服务双重安全配置]]**                              | 网关层鉴权，服务层也有安全保障          |

### 具体是怎么设计的

**Spring Security 配置（BaseSecurityConfig）：**
- 禁用 CSRF 保护
- 采用无状态会话管理
- 添加 JWT 认证过滤器
- 子服务继承后配置具体路径权限规则：Swagger、登录、注册放行，其他接口需认证

```java
applyBaseSecurityConfig(http);
// 配置路径权限：Swagger、登录注册放行，其他需要认证
```

**CORS 跨域策略：**
- 预留跨域配置扩展点
- 实际项目可按需配置允许的源、HTTP 方法、请求头等，支持前后端分离架构

**请求防护：**
- 网关日志记录所有请求信息（路径、方法、用户 ID、时间戳等），发送到消息队列
- 网关告警机制：对未授权请求、无效令牌等异常情况发送告警消息，便于监控

### 为什么不采用其它方案

| 方案                         | 原因                               |
| -------------------------- | -------------------------------- |
| **不启用CSRF保护**              | API服务使用Token认证，CSRF风险较低，同时简化了配置； |
| **不采用复杂的权限框架**             | 当前需求简单，基础的角色控制足够，避免过度设计；         |
| **不在每个服务都做鉴权**             | 网关统一鉴权效率更高，减少重复代码，便于统一管理。        |
| **基础配置继承 + 网关双重安全（选择了这个）** | 统一配置避免重复，网关+服务两层防护无盲区            |

## 三、密码安全设计

### 解决了什么问题

**核心矛盾：** 密码明文存储存在数据库泄露风险，用户倾向弱密码易被破解，登录接口缺乏暴力破解防护，输入格式不统一校验困难

**解决方案：** BCrypt 加密 + 密码强度校验 + 用户状态管理 + 统一参数校验工具

**效果：** 数据库泄露不直接暴露明文，引导用户设置强密码，预留暴力破解防护，输入格式统一校验

### 为什么这么设计

| 设计选择 | 为什么这么定 |
|---------|------------|
| **BCrypt 加密算法** | 自带盐值防止彩虹表攻击，计算成本高增加暴力破解难度 |
| **统一参数校验工具** | 避免各接口重复编写校验代码，确保输入格式一致 |
| **用户状态管理（状态字段）** | 可禁用异常账号，支持账号管控 |
| **事件日志记录（登录、注册等）** | 便于安全审计和异常行为追踪 |

### 具体是怎么设计的

**BCrypt 加密存储（BCryptPasswordEncoder）：**
- 注册时加密密码存入数据库，不保存明文
- 登录时用相同算法验证密码是否匹配

```java
// 注册时加密密码
user.setPassword(passwordEncoder.encode(registerDTO.getPassword()));
// 登录时验证密码
passwordEncoder.matches(loginDTO.getPassword(), user.getPassword())
```

**密码强度校验：**
- 要求包含大小写字母、数字和特殊字符，长度至少 8 位
- 注册时调用校验工具验证，不符合要求则提示用户

**登录安全管理：**
- 用户表设计状态字段，支持禁用异常账号
- 预留登录失败重试限制扩展点：可使用 Redis 记录失败次数，达到阈值后临时锁定账号，防止暴力破解

**其他参数校验：**
- 用户名、邮箱、手机号等进行非空和格式校验
- 邮箱使用正则表达式验证格式
- 手机号验证国内手机号格式

### 为什么不采用其它方案

| 方案 | 不采用的原因 |
|------|------------|
| **MD5 / SHA 加密** | 计算速度太快，容易被暴力破解；需手动管理盐值，安全性不如 BCrypt |
| **第三方认证服务** | 增加外部依赖和成本，用户数据不在自己掌控中 |
| **过于复杂的密码策略** | 当前设计已满足基本安全需求，过度复杂影响用户体验 |
| **BCrypt + 强度校验 + 状态管理（选择了这个）** | 自带盐值抗彩虹表，校验引导强密码，状态管理可停用异常账号 |

## 总结

双 Token 实现无状态认证，网关层集中鉴权，服务层继承基础安全配置，密码使用 BCrypt 加密存储。预留了 Token 黑名单、CORS 配置、请求限流、登录失败重试限制等扩展点，后续可根据需要逐步完善。
