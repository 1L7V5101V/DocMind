## 一、RabbitMQ配置设计

### 解决了什么问题

解决了交换机与队列绑定问题，不同服务有独立的交换机和队列，避免相互干扰；解决了消息持久化问题，服务重启后消息不丢失；解决了消息传递架构问题，支持异步解耦、流量削峰。避免某个接口因为下游服务调用使得响应时间过长，例如AI接口的调用，采用异步的方式，用户无明显延迟感知。

### 为什么这么设计

采用TopicExchange主题交换机，支持灵活的路由键匹配；每个服务有独立的交换机和队列，服务自治，互不影响；队列和交换机都设置为持久化，保证消息可靠性；使用点分隔命名规范（如user.register.queue），清晰易读；JSON序列化消息，支持复杂对象传输。

### 具体怎么设计的

- 交换机与队列绑定 ：每个服务配置独立的TopicExchange交换机，如user.exchange、file.exchange、gateway.exchange。每个交换机绑定多个队列，使用不同的路由键区分。例如用户服务绑定用户注册队列、密码重置队列、操作日志队列，分别对应user.register、user.password.reset、user.operate.log路由键。

```
// 交换机队列绑定示例
@Bean
public Binding bindingUserRegisterQueue() 
{
    return BindingBuilder.bind
    (userRegisterQueue()).to(userExchange
    ()).with(USER_REGISTER_ROUTING_KEY);
}
```

- 消息持久化策略 ：所有队列和交换机都配置为持久化（durable=true），服务重启后不丢失。队列配置为非排他、非自动删除，保证多实例消费可用。消息默认使用持久化投递模式，写入磁盘。
- 消息确认机制 ：使用RabbitTemplate发送消息，默认开启生产者确认和消费者手动确认扩展能力。当前使用@RabbitListener注解消费消息，框架自动处理确认，后续可扩展为手动确认模式，增加可靠性。使用Jackson2JsonMessageConverter进行JSON序列化，支持对象消息传输。

### 为什么不采用别的方式

- 不采用FanoutExchange扇形交换机，因为不需要广播到所有队列，TopicExchange更灵活；
- 不采用DirectExchange直连交换机，因为TopicExchange支持通配符匹配，扩展性更好；
- 不采用非持久化队列，因为会导致消息丢失，可靠性不足；不使用JDK序列化，因为JSON更通用、跨语言支持更好。

## 二、消息消费者设计

### 解决了什么问题

解决了异步文件处理问题，文件上传下载等耗时操作异步执行；解决了文档索引更新问题，文件变更后异步更新搜索索引；解决了用户通知推送问题，注册、密码重置等场景异步发送通知；解决了日志记录问题，网关日志、操作日志异步处理不影响主流程。

### 为什么这么设计

使用@RabbitListener注解声明消费者，简洁易用；每个队列对应独立的处理方法，职责清晰；消息消费异常只记录日志，不影响主流程；支持多实例并发消费，提高处理能力；异步解耦，主流程快速返回，提升用户体验。

### 具体怎么设计的

- 异步文件处理 ：文件服务监听文件上传、下载、处理、删除队列。上传完成后发送消息，异步处理文件元数据统计、热度计算等；下载完成后发送消息，异步记录下载日志、更新下载次数；文件处理队列支持格式转换、OCR识别等异步任务；删除操作发送消息，异步清理关联索引和缓存。

```
// 消息消费者示例
@RabbitListener(queues = RabbitMQConfig.
                FILE_UPLOAD_QUEUE)
public void handleFileUploadMessage
(Map<String, Object> message) {
    // 处理文件上传后的异步任务
}
```

- 文档索引更新 ：预留文档索引更新扩展点，文件内容变更后发送消息，异步更新ES或向量数据库索引，保证搜索实时性。
- 用户通知推送 ：用户服务监听用户注册、密码重置队列。注册成功后发送消息，异步发送欢迎邮件；密码重置发送消息，异步发送重置链接邮件；操作日志队列异步记录用户操作行为，用于审计和数据分析。
- 网关日志告警 ：网关服务监听日志和告警队列，记录所有请求日志，异常情况发送告警，异步处理不影响网关性能。

### 为什么不采用别的方式

- 不使用同步处理，因为会阻塞主流程，影响响应时间；
- 不使用多线程池代替MQ，因为无法持久化、无法削峰、可靠性差；
- 不使用Kafka，因为RabbitMQ更适合业务消息场景，功能更丰富，延迟更低；
- 不直接调用其他服务接口，因为耦合度高，一个服务故障会影响另一个服务。

## 三、消息可靠性设计

### 解决了什么问题

解决了消息丢失问题，异常消息不丢弃；解决了消息重试问题，临时故障自动重试；解决了消息重复消费问题，保证幂等性。

### 为什么这么设计

预留死信队列扩展点，当前先保证基础功能可用；预留消息重试机制，使用Spring Retry或手动重试；预留幂等性保障，使用消息ID或业务唯一键；架构设计上考虑了可靠性，后续可逐步完善。

### 具体怎么设计的

- 死信队列配置 ：预留死信队列（DLQ）扩展设计，当消息消费失败、过期、队列满时，将消息转发到死信交换机，通过死信队列统一处理异常消息，定期人工介入或自动分析，保证消息不丢失。
- 消息重试机制 ：预留消息重试配置，使用Spring的重试机制，设置最大重试次数和重试间隔，指数退避策略，避免频繁重试压垮服务。重试超过最大次数后，消息进入死信队列。
- 消息幂等性保障 ：预留幂等性设计，使用消息唯一ID或业务主键（如fileId、userId），消费前检查是否已处理，使用Redis记录已消费的消息ID，或数据库唯一索引防止重复处理。

### 为什么不采用别的方式

- 不直接丢弃失败消息，因为会导致数据不一致；
- 不使用无限重试，因为会造成资源浪费和死循环；
- 不依赖MQ的去重，因为MQ只保证至少一次投递，需要业务层实现幂等；
- 不一开始就实现所有可靠性机制，因为当前阶段先保证核心流程可用，后续根据需要逐步完善。

## 总结

RabbitMQ设计采用每个服务独立的TopicExchange交换机，队列和交换机持久化，JSON序列化消息。使用@RabbitListener注解消费消息，实现异步文件处理、用户通知、日志记录等功能。预留了死信队列、重试机制、幂等性保障等可靠性扩展点，当前已实现基础的消息发送和消费功能，后续根据需要逐步完善可靠性机制。
