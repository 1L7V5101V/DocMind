## 一、存储架构设计

### 解决了什么问题

**核心矛盾：** 不同场景需要不同存储方式（[[本地开发_生产分布式]]），大文件直接上传易超时失败，存储类型缺乏统一管理，扩展性差

**解决方案：** 策略模式 + 多层抽象，通过配置文件切换存储后端；分片上传支持大文件；预留 S3 扩展

**效果：** 环境无关存储切换、大文件可靠上传、存储后端可扩展

### 为什么这么设计

| 设计选择 | 为什么这么定 |
|---------|------------|
| **策略模式 + 配置文件切换存储类型** | 开发环境本地存储，生产环境分布式存储，按环境灵活切换 |
| **多层抽象（FileService 接口 + 实现）** | FileService 定义统一操作，FileServiceImpl 根据配置切换后端 |
| **容错设计** | 数据库不可用时不影响文件存储，降级处理 |
| **预留 S3 存储类型** | 后续可扩展接入 AWS S3，渐进式设计 |

### 具体是怎么设计的

**配置层：** FileStorageConfig 统一管理存储配置（支持配置：存储类型、本地路径、最大文件大小、MinIO [[桶名]]）

**存储类型枚举（StorageTypeEnum定义三种存储类型）：**
```Java
LOCAL("local", "本地存储")
MINIO("minio", "MinIO存储")
S3("s3", "AWS S3存储")
```

**分片上传策略：**
- 前端分片：ConcurrentHashMap 暂存分片
- 合并：按顺序读取分片合并写入目标存储
- 清理：合并完成后删除临时分片

**MinIO 集成：** MinioConfig 配置 MinIO 客户端

**设计特点：**
- 统一接口，易于扩展新存储类型
- 容错设计，数据库故障不影响文件操作
- 分片上传支持大文件
- 配置驱动，切换存储方式无需改代码

### 为什么不采用其它方案

| 方案                         | 不采用的原因                      |
| -------------------------- | --------------------------- |
| **固定单一存储**                 | 开发环境本地存储方便，生产需要分布式存储；无法灵活切换 |
| **直接文件系统读写**               | 缺少元数据管理、权限控制、分布式支持          |
| **复杂的存储网关**                | 过度设计，当前需求不需要；增加复杂度与维护成本     |
| **[[策略模式 + 多层抽象]]（选择了这个）** | 配置驱动灵活切换，容错设计，预留扩展          |

## 二、文件元数据设计

### 解决了什么问题

1. **文件信息管理**问题 ：需要记录文件的各种元数据信息
2. **文件追踪**问题 ：需要知道文件存放在哪里、多大、什么类型
3. **文件版本**问题 ：需要支持文件版本管理（预留设计）
4. **文件权限**问题 ：需要控制谁能访问文件

### 为什么这么设计

| 设计选择           | 为什么这么定            |
| -------------- | ----------------- |
| **数据库 + 存储分离** | 文件内容存存储后端，元数据单独管理 |
| **UUID 作为主键**  | 避免文件名冲突，便于跨存储管理   |
| **状态字段**       | 支持软删除等操作          |
| **创建/更新时间戳**   | 便于追踪文件操作记录        |

### 具体是怎么设计的

**文件元数据表结构（FileMetadata）：**

```java
@TableName("file_metadata")
public class FileMetadata {
    @TableId(type = IdType.ASSIGN_UUID)
    private String id;                    // 主键UUID
    private String fileId;                // 文件ID
    private String fileName;              // 文件名
    private String originalFileName;      // 原始文件名
    private String filePath;              // 文件路径
    private String fileType;              // 文件类型
    private long fileSize;                // 文件大小
    private String md5;                   // 文件MD5
    private String storageType;           // 存储类型
    private String bucketName;            // 存储桶名
    private String objectKey;             // 对象键
    private String status;                // 状态
    private String createBy;              // 创建者
    private LocalDateTime createTime;     // 创建时间
    private LocalDateTime updateTime;     // 更新时间
}
```

**文件类型枚举（FileTypeEnum）：**

```java
public enum FileTypeEnum {
    IMAGE("image", "图片文件"),
    DOCUMENT("document", "文档文件"),
    VIDEO("video", "视频文件"),
    AUDIO("audio", "音频文件"),
    ARCHIVE("archive", "压缩文件"),
    OTHER("other", "其他文件")
}
```

**设计特点：**
- 双 ID 设计（id （主键UUID）和 fileId（文件ID）），便于扩展
- 完整元数据信息
- 支持多种存储类型适配
- 预留状态管理

### 为什么不采用其它方案

| 方案                   | 不采用的原因            |
| -------------------- | ----------------- |
| **文件名作为标识**          | 文件名可能冲突，不便于跨存储迁移  |
| **JSON 存储元数据**       | 查询效率低，不便于事务管理     |
| **复杂版本控制**           | 初赛先简化设计，后续可扩展     |
| **数据库表存储元数据（选择了这个）** | 查询高效，支持事务，结构清晰易维护 |

## 三、文件操作设计

### 解决了什么问题

1. **文件操作标准化**问题 ：上传、下载、删除、重命名等操作需要统一接口
2. **文件安全**问题 ：需要校验文件类型和大小限制
3. **用户体验**问题 ：需要支持文件预览功能
4. **操作审计**问题 ：需要记录文件操作

### 为什么这么设计

| 设计选择 | 为什么这么定 |
|---------|------------|
| **RESTful API 设计** | 统一的接口风格，前端集成友好 |
| **分层设计（Controller → Service → Storage）** | 各层职责清晰，便于测试和替换 |
| **事件驱动（RabbitMQ）** | 文件操作事件解耦，异步处理非核心逻辑 |
| **容错处理** | 数据库不可用时降级，保证文件操作可用 |

### 具体是怎么设计的

**文件服务接口（FileService）：**

```java
public interface FileService {
    String upload(MultipartFile file);                         // 单文件上传
    String[] uploadMultiple(MultipartFile[] files);            // 多文件上传
    void uploadChunk(MultipartFile chunk, String fileId, int chunkIndex, int totalChunks); // 分片上传
    String mergeChunk(String fileId, String fileName);         // 分片合并
    byte[] download(String fileId);                            // 文件下载
    void delete(String fileId);                                // 文件删除
    void rename(String fileId, String newName);                // 文件重命名
    void move(String fileId, String targetPath);               // 文件移动
    String copy(String fileId, String targetPath);             // 文件复制
}
```
**文件操作流程 **：
- **上传流程：**
	1. 生成文件 ID（UUID）
	2. 根据存储类型写入存储后端
	3. 保存元数据到数据库（容错）
	4. 发送 RabbitMQ 事件

- **下载流程：**
	1. 从数据库获取元数据
	2. 根据存储类型读取文件
	3. 返回文件内容

- **删除流程：**
	1. 从数据库获取元数据
	2. 从存储后端删除文件
	3. 删除元数据（容错）

**文件校验：**
	- **大小限制：** FileStorageConfig 配置 maxSize
	- **文件类型校验：** 通过 fileType 字段记录
	- **文件预览：** 复用下载接口，直接返回文件内容

**事件通知：** 通过 RabbitMQ 发送文件上传、下载、删除事件

### 为什么不采用其它方案

| 方案 | 不采用的原因 |
|------|------------|
| **直接文件系统权限控制** | 不便于跨平台和分布式部署 |
| **WebDAV 协议** | 学习成本高，不便于集成现有架构 |
| **复杂工作流引擎** | 过度设计，当前需求不需要 |
| **RESTful + 分层 + 事件驱动（选择了这个）** | 接口统一、职责清晰、异步解耦、支持容错 |

## 总结

- **存储抽象：** 统一的存储接口，便于扩展
- **容错设计：** 数据库故障不影响文件操作
- **[[事件驱动]]：** 通过 RabbitMQ 解耦文件操作
- **配置驱动：** 通过配置文件灵活切换存储方式
